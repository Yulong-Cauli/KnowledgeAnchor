# Claim 卡片内容改进实施任务

编写与修订日期：2026-11-04。接手对象：Sol。

目标：**在讨论论文 IDEA、分析实验现象和设计实验时，能够调用库内有出处、有适用边界的结论、知识与经验，提出值得检验的问题，并设计能改变判断的实验。**

一张卡几个月后被单独检索出来，读者仍应知道：它具体声称什么、证据支持到哪里、为什么可能发生、有哪些其他解释、迁移到当前问题时要检查什么，以及下一步怎样检验。卡片既要支持追溯，也要保留继续推理所需的信息。

当前模板已有 `scope / evidence / falsifiers / related` 和正文，足以承载这一目标。本次改进重点是内容质量与研究用途，不以增加字段、卡片数量或篇幅作为完成标准，也不要求每张卡都产生一个新 IDEA。

本文是后续实施任务书，尚未执行卡片改写。本次修订只更新任务书。网页功能任务另见 [01-网页可用性改进实施任务.md](01-网页可用性改进实施任务.md)。

## 1. 范围与权限

- 先读 [AGENTS.md](../AGENTS.md)。可以整理 `status: asserted` 的卡片、改进 [模板](../templates/claim.md)和配套说明；已有 `verified / refuted / stale` 卡不得修改，任何 `signoff` 不得代填或改动。
- 默认保留现有 id、文件名、status、stance、review_due。内容编辑不等于用户复核，也不应顺延日期或替用户改变立场。
- 已提交或被引用的 id 是稳定标识，不能因为改写标题而改名。不得把旧 id 悄悄改成另一个命题。
- `library/` 在此任务中只读。发现笔记问题，在整理报告中给具体位置和建议；本任务书不提供修改来源笔记的额外授权。
- 优先修改正文表达和现有字段内容，不为排版方便增加大量必填元数据，也不要求一次变更整个 schema。
- 先用三张卡形成样板，再按主题分批审阅现有 asserted 卡。无需为了统一形式而改动本来清楚的卡；涉及实质命题替换、证据不足或用户状态决策的条目保留并列入待决清单，继续完成其余条目。
- 本轮整理已有知识及其研究用途。可以在正文提出有依据、明确标记为尚未验证的候选解释与实验问题；不因整理任务自动启动训练、采购、部署或更改项目方案。

## 2. 内容标准

### 2.1 一张卡只承载一个可证伪主张

- 标题用一句话表达主张，保留决定结论的关键条件；配置清单、完整数字表和机制细节移到 scope 或正文。
- 判断是否需要拆分，看各部分是否需要不同证据、能否独立成立/被推翻，不能只按字数拆卡。
- “论文报告了某个数字”与“相同条件下可复现该效果”是不同命题。前者主要核对原文，后者需要独立证据；标题、scope、evidence、falsifiers 必须围绕同一命题。
- “定义/构造是什么”“为何理论成立”“实证效果如何”也应区分。纯背景定义可在正文解释并引用 L1，未必需要额外建卡。
- 若确需拆分：只有已有准确来源的独立主张才新建 asserted 卡，并用 `related` 关联；保留原卡原 id 与原命题，说明范围重叠或待处理事项。旧卡是否退休/改变状态由用户决定，不为了拆卡擅自删卡或改状态。

### 2.2 先讲明白，再讲完整

“这条主张是什么意思”用两三句话回答：研究者在解决什么问题、主张发生了什么、为什么值得理解。必要术语首次出现给短解释，小例子必须标明是解释性示例，不能伪装成论文实验。

避免把摘要换几个词抄入“我的理解”，也避免把全部数字、缩写和限定塞进一个长段落。精确数据只在需要的位置呈现，保留指标单位、比较方向、基线与数据划分。

按内容需要，检查卡片能否回答下面六个问题。答案可以分布在现有字段和正文中，不必为每个问题另设字段，也不要求没有依据时凑出答案。

| 问题 | 对研究讨论的作用 |
|---|---|
| 发现了什么现象或提出了什么主张？ | 明确需要理解或检验的对象，避免只剩方法名称和排行榜数字。 |
| 证据实际支持到哪里？ | 区分论文报告、实验观察、理论推导与独立验证，暴露证据缺口。 |
| 为什么可能发生，还有哪些其他解释？ | 形成可检验的机制假设，避免把作者叙事直接当成因果结论。 |
| 在哪些条件下成立，迁移时什么会变？ | 判断与当前问题的关系，区分原范围内结论与跨任务外推。 |
| 哪个检查或实验能区分这些解释？ | 让下一步有信息增益，而不只重复报告一个分数。 |
| 不同结果分别意味着什么？ | 说明结果会改变哪项判断、下一步继续检查什么。 |

### 2.3 区分来源报告、解释与个人判断

| 内容 | 写法要求 |
|---|---|
| 来源报告 | “论文声称 / 作者报告（尚未独立验证）……”并给来源及定位。原文说了什么与实际效果是否成立分开。 |
| 解释或推断 | 明确标出“这里的解释 / 推测是……”，说明依据和推断跨度，不把自己的因果解释归给作者。 |
| 个人实验记录 | 说明谁在什么配置下实际做过什么，链接配置、日志和结果；未由用户签署的 claim 仍是尚未独立验证的 asserted。 |
| 研究启发 | 明确标为候选问题或待检验假设，写出从已有证据到新问题的推理，不把启发写成现成结论。 |
| 当前立场 | 解释现有 stance 的依据；若原卡没有留下依据，就写“立场依据未记录”，不要替用户补造理由。 |
| 下一步 | 写清待核查的材料、比较对象或最小实验，以及结果会怎样改变对该命题的判断。 |

`status` 与 `stance` 必须一起保留。`asserted` 的正文、摘要和影响分析都不能写成已验证事实；高风险选型、部署和方案结论只使用 verified。

尚未验证的论文主张可以参与 IDEA 讨论，作为待检验假设的来源；不需要先将全库升级为 verified 才开展研究讨论。每次调用仍须保留 claim id / 来源、status、stance，并说明与当前问题相关的 scope。

核对“论文确实这样写”、独立复现“同配置下出现该效果”、检验“能否迁移到新任务”是不同的证据。即使卡片以后由用户签署为 verified，也只能用于实际核查的命题与范围，不能把原文核对视为效果复现或跨项目适用的证明。

### 2.4 Scope 与 falsifiers 对齐

经验结果的 scope 推荐顺序：数据集与 split → 模型/版本 → 输入/训练/推理条件 → 比较基线 → 指标口径。仅写与主张有关的条件；理论卡写假设、对象、推导条件，不强填数据集/硬件。

每条 falsifier 要回答：**在声明条件仍满足时，什么观察或反例会使这条主张不成立？**

- 换模型、换数据集后失效，通常属于外推限制，移到迁移检查，不能直接充当原范围内的反证。
- “尚未复现成功”“原文暂时找不到”“单次运行不显著”不能自动写成已推翻。
- 效应大小、误差容限或统计阈值需要依据。若为拟议实验标准，明确标为预设且待确定，不随意编数字。
- 对来源陈述的核查与实际复现分别列出，不用一种结果冒充另一种证明。
- scope 中的限制在正文结尾仍有效，不能在“意义”段突然扩大成整个模型家族或所有数据集的结论。

### 2.5 原文、转述与历史证据分别保留

- `quote` 只写逐字原文。翻译、表格重排、数字摘录说明、自己的概括放正文并明确标记；不得把转述包装成直接引文。
- 引用优先指向 `library/` 笔记，并给章节/页码。核查理论或实验出处时追到原论文/官方实现；本轮没读过的外部资料不能标成“已核对”。
- `source`、`locator`、`quote` 必须相互匹配；不要用笔记小节号冒充论文小节号。原论文和笔记定位分别注明。
- 数学符号需核对上下标、指数、负号、归一化条件。PDF/HTML 转换或现有笔记可能丢失格式；不得凭记忆修复公式。
- 来源变化后，旧引文只能作为明确标记的历史记录。若可查到历史提交/版本，记录实际版本定位；查不到就注明历史来源待定位，不能编造 hash、页码或永久链接，也不能继续把它当作当前笔记的逐字引文。
- 当前证据含有疑点时，保留问题与来源缺口，停止对该条做实质结论重写。不能为通过 `validate` 填造 quote 或空泛证据。

### 2.6 保留不同种类的研究知识与经验

按内容选择整理重点，不必新增卡片类型字段，也不必将每张卡都写成“某方法提升多少”。

| 内容 | 应保留的信息 | 应避免的概括 |
|---|---|---|
| 实验观察与结果 | 比较对象、控制条件、指标口径、效应及已记录的波动；哪些变量同时改变。 | 将整套方法的提升直接归因于其中一个模块。 |
| 机制与方法知识 | 要解决的问题、方法如何作用、依赖的假设、支持机制的证据及其他可能解释。 | 将设计动机或合理直觉写成已证实的因果机制。 |
| 理论主张 | 原始命题、假设、符号、推导出处与关键步骤，以及证明没有覆盖的情形。 | 将近似、建模假设或经验规律写成无条件定理。 |
| 失败与负面经验 | 实际尝试、配置、失败现象、排查证据、已排除和仍未排除的解释。 | 将一次运行失败、复现未成功或特定配置无收益概括为整条路线无效。 |
| 评测与实验经验 | 指标盲区、数据划分、泄漏风险、对照条件和发现误判的检查方法。 | 把某指标改善直接写成整体能力改善。 |

定义、公式和完整背景推导可以继续留在 `library/`；需要反复调用、具有明确条件且可检验的判断再提炼为 claim。现有笔记有缺口时提出修改建议，本任务不直接改写 `library/`。

个人实验经验也可以成为来源，但必须有可追溯记录。优先链接已有笔记；配置、日志和结果文件可作为补充证据，并标明实际版本、运行范围与定位。没有记录时登记为待补材料，不凭印象补造实验过程，也不为建卡绕过现有必填证据要求。

### 2.7 把下一步写成能区分解释的检查或实验

对经验结果和机制卡，下一步不能只写“复现一下”或“试试能否提高精度”。优先给一个最小、可执行的检查，按问题需要交代：

1. **要区分什么。** 写清待检验解释与至少一个有依据的替代解释；没有足够依据提出机制时，先核查来源或测量现象，不编造机制。
2. **改变什么、固定什么。** 指明干预或替换项、比较基线和需要保持一致的条件。参数量、训练预算、输入信息等若无法匹配，说明它们仍可能解释差异。
3. **观察什么。** 选择直接对应问题的指标或诊断量；必要时补充分场景、分类别、输出变化或开销检查，不能只依赖一个汇总分数。
4. **结果如何改变判断。** 分别说明支持候选解释、削弱候选解释和暂时不能区分时意味着什么。性能提升本身通常不足以证明具体机制；没有观察到差异也不自动等于证明等效。

区分四类下一步：原文核查、同范围复现、机制辨别、跨条件迁移。它们可以相互补充，但不能用一种结果替代另一种证据。理论卡可用推导核对、边界情形或反例检查，不强行安排模型训练。

效应阈值、重复次数与预算应按实际问题和已有证据确定；未知时明确待确定，不任意填数字。这里要求写清实验思路，不要求本轮执行全部实验。

### 2.8 保留研究启发与跨卡推理的来路

- 说明该卡有助于理解哪类问题、识别哪类失败或设计哪类对照。没有明确项目背景时，写问题与适用条件，不替用户指定研究方向或推荐默认方案。
- 从多张卡提出候选解释时，列出实际使用的 claim id / 来源、status、stance 和各自 scope，说明哪些证据可比较、哪些条件不同。多篇论文说法相似，不自动构成同一机制的独立验证。
- `related` 只表达有关联；在正文说明关联是支持、张力、条件差异还是共享待检验问题。不同数据集、指标或模块位置出现不同结果，先检查是否可比，不能直接称为互相推翻。
- 新问题应明确写为“由这些材料提出的研究假设，尚未验证”，保留推断步骤及缺口。没有直接证据的新假设先放在正文的研究启发中，不为增加卡片数量把它包装成已有实证结论。
- 原子性约束的是核心命题，不要求删去理解该命题所必需的上下文、解释和实验思路。纯勘误或来源核查卡可以提供引用与评测上的帮助，不必硬凑一个创新点。

## 3. 推荐正文结构

复用已有 frontmatter：`title / scope / evidence / falsifiers / related` 等仍是结构化字段。正文解释它们，避免把这些字段逐字重复一遍。

```markdown
## 这条主张是什么意思

用两三句话解释问题与主张。asserted 卡明确说明尚未独立验证。

## 证据支持到哪里

说明哪条引文/表格/实验记录支持哪一部分；区分来源报告与独立验证。
写出仍缺失的证据，不把“读到原文”写成“效果已复现”。

## 可能的解释与未排除的因素

按需要区分作者解释、已有验证与自己的推测，给出依据。
说明现有对照排除了什么、仍有哪些解释；没有依据时明确未知。
理论卡可改为“假设与推导”，保留原始出处和关键步骤。

## 适用范围与迁移限制

解释 scope 中真正影响结论的条件。
需要迁移到其他项目时，说明还需验证哪些变化。

## 对研究问题的启发

说明这条知识能帮助理解什么问题、识别什么失败或提出什么候选假设。
明确区分已有结论与研究启发；涉及其他卡时保留 id、status、stance 和条件差异。

## 当前立场与下一步

保留当前 stance；只写已有记录支持的理由。
给一个优先执行的最小检查：要区分什么、改变和固定什么、观察什么。
说明不同结果如何改变对这条具体主张或候选解释的判断。
区分原文核查、同范围复现、机制辨别和跨条件迁移。

## 核查记录

按日期记录实际完成的核对、发现和未解决事项。
没有记录时不虚构；本轮仅做表达整理就如实写表达整理。
```

这是推荐结构，不要求逐节填满。可按内容合并或省略不适用的小节，信息完整而简短的卡无需扩写。没有核查历史可省略最后一节；已有记录应移到末尾保留，不删去关键的修正经过。理论推导需要保留出处和步骤，不能为了简短把证明依据删掉。

## 5. 执行顺序

### 阶段 A：盘点与三张样板

1. 记录执行前的文件状态，列出 asserted 与受保护卡；保存用于核对的受保护卡/签署字段摘要或 hash。此处完整性核对 hash 不是 claim 的 `signoff.evidence_hash`，不得填入签署。
2. 选择实验结果、机制/行为观察、理论主张各一张作为样板，优先参考上表；读取来源笔记和必要原始来源，核对命题范围后整理。结合表中实验辨别、负面结果的参考检查表达方式，找不到依据的部分明确留缺口，不为凑样板补造证据。
3. 根据样板调整 `templates/claim.md` 的正文提示；保持新卡 `asserted`、原有签署占位约定与必填证据规则。
4. 更新 `web/app.js` 的 `NEW_CARD_BODY` 等新建正文来源，使网页起草与文件模板一致。网页正在由另一项任务修改时，先对照现有差异再合并，不覆盖其他实现。
5. 用一个与样板相关的假想讨论问题做桌面检查，明确标为整理者设计的情境，不伪装成真实项目结果：读者能否复述主张、范围与证据缺口，并据此提出有依据的问题和一个能改变判断的检查？理论卡可以用推导与反例检查完成。阶段 A 是内部质量检查，不需要对每张卡新增一次用户批准流程。

### 阶段 B：分主题整理 asserted 卡

- 按目录/研究主题分批，逐卡检查原子性、标题与 scope 一致性、证据原文、推断跨度、falsifiers、历史记录、研究用途和下一步。注意失败、负面结果与评测经验，不只整理正向性能增益。
- 对实际存在的跨卡联系，在正文说明关系与条件差异；能提出待检验问题就保留推理来路，不能比较就明确缺口，不批量生成没有证据的“通用规律”。
- 对表达整理、证据核对、命题范围变化分别记录，避免将统一改标题的脚本冒充内容审阅。
- 现有内容合格的标记为已审阅保留；证据不足/需要原命题决策的条目进入待决清单，不阻塞其他卡片。
- 不以卡片数量增长为目标，不批量推断用户立场，不自动延后 review_due，不批量修改来源笔记。
- 本轮不要求跑完全部模型复现实验；“整理卡片”与“验证论文结论”是不同交付。执行了什么核对就报告什么。

### 阶段 C：字段说明与收尾

网页显示名称可使用下面的对应，存储键保持兼容：

| 字段 | 建议说明 |
|---|---|
| status | 验证状态：这条主张目前经过什么程度的确认。asserted 表示尚未独立验证。 |
| stance | 当前立场：adopt 采用 / trial 试验 / watch 关注 / avoid 避免；它不替代验证状态，也不越过 verified 的高风险使用门槛。 |
| scope | 主张成立所限定的条件。 |
| evidence | 支持或反对主张的来源材料；可查看原文和定位。 |
| falsifiers | 在限定条件内，会使我撤回主张的结果。 |
| review_due | 下次处理日期；改日期不表示验证通过。 |
| related | 有关联的其他 claim；关联不等于支持。 |
| signoff | 用户本人填写的验证签署；网页与 Agent 均不代签。 |

网页默认阅读、显式编辑的具体实现归第一份任务；此处负责说明内容与新卡正文的一致性。正文小节不必分别对应表单字段，不能为统一展示强制所有卡填写同一组空泛段落。

## 6. 验收与交付

### 内容验收

- 每张实际改动的卡能指出一个明确命题，标题、scope、证据和 falsifiers 相互对应。
- asserted 均按未独立验证表达；没有把单模型/单数据集观察扩大为普遍结论。
- 来源报告、自己的解释和用户立场分得清；没有伪造 quote、locator、source、实验结果或用户意见。
- 经验与机制卡能区分观察到的结果、候选解释和仍未排除的因素；理论卡能指出假设、推导依据和适用边界。未提供机制证据时不补写因果结论。
- 当前情况先于核查历史；重要历史和证据版本可追踪。缺少历史版本时明确标注，不补造出处。
- 下一步可执行，说明检查对象、比较或推导方式及结果含义；超出 scope 的迁移检查与原命题反证分开，不用“复现一下”代替具体问题。
- 研究启发明确标为尚未验证，能追溯到具体证据与推理；跨卡讨论保留各卡 id / 来源、status、stance 和条件差异，不把 related 当成支持关系。
- 失败与负面经验保留运行范围和未排除的解释；没有把单次失败判为路线无效，也没有把核对原文写成效果已复现。
- 三张样板通过第 5 节的讨论情境检查；不以增加卡片数量、统一小节数量或要求全库先 verified 代替研究用途验收。
- 所有原 id、文件名保持稳定；既有 stance/review_due 默认保持，所有 signoff 与受保护卡不变，library 不变。

### 工具检查

每批运行 `node tools/ka.mjs validate`，结束运行 `node tools/selftest.mjs` 与 `git diff --check`；需要更新索引时只运行 `node tools/ka.mjs index`，不手改派生索引。

检查引文在当前来源或已记录历史版本中是否逐字匹配；数学和表格仍需人工式对照，不能把字符串命中当作结论成立。结构校验通过也不代表内容已验证。

### 交付报告

在 `tmp_docs` 留一份实施结果，记录：

- 三张样板及实际采用的表达规范；全库审阅/改动/原样保留/待决的数量。
- 三张样板的讨论情境、可以提出的研究问题、建议检查和结果解释；注明哪些来自现有证据、哪些是整理者提出的待检验推断。这里只验证卡片是否便于推理，不宣称 IDEA 已有创新性或实验已执行。
- 每张改动卡的 id、status、stance、改动类型和来源核对范围；新建拆分卡另列来源与关联关系。
- 待决条目的具体问题、已找到的证据、为什么不能直接完成；不要只写“待人工确认”。
- 非 asserted 卡、signoff、原 id、library 的保留检查结果；未提交的其他工作是否被完整保留。
- 校验结果与未完成范围。不能把完成三个样板报告为完成全库整理，也不能将内容整理报告为 verified。

保留用户原有改动，不擅自提交或推送。
