## 0 · 判断标准与一个关键前提

**立卡门槛**（四条同时满足才建议立卡）：

1. 能写成一条可证伪主张（写得出"什么结果会推翻它"）；
2. 有前向决策价值——将来做选型、设计实验或写方案时会引用它；
3. scope 写得死（硬件 / dtype / 模型配置 / 软件版本 / commit）。**版本依赖不是否决项，而是 scope 的组成部分**：把 commit 钉进 scope，主张就变成可判定的快照主张；
4. 证据扎实：笔记有章节 locator，quote 可逐字验证（本次已验证）。

**关键前提**：三篇笔记记录的都是用户本人发起并合入的 Liger PR，基准数字是一手实测且 PR 评论区带原始日志——证据地位好于"论文自报数字"。这直接拆掉了原始疑虑的一半：**立卡不依赖第三方复现**；独立验证是卡上"待验证"栏的工作（status 保持 asserted，由主人本人 verified），不是立卡的前提。剩下的另一半「版本依赖强」按第 3 条处理：钉进 scope。

**不立卡的判据**（出现任一条 → 留在 L1）：

- 教科书级数学推导（不是经验主张，无"验证"可言）；
- 版本考古快照，且其问题已随合入永久修复（对未来决策零输入价值）；
- 过程复盘 / 方法论叙事（无法写成单一可证伪主张，价值已由 L1 的方法论清单承载）；
- 上游内部实现快照，且上游明确还在动（很快 stale）。

### 理由

- 版本依赖可控：主张钉在 PR #1423 合并 squash（`f6385e9`）上。上游 FLCE 后续改动（#1468/#1472，笔记 §04 自己记录了）不影响快照主张的成立性，只影响"现行 main 是否仍然如此"——那是 review_due 重验的事。

### 草案 A：`claim-liger-fusedkl-mem-not-speed`

- **title（建议）**：Liger FusedLinearKLDivLoss 相对 torch 朴素路径的收益是峰值显存而非速度（full 时间持平）
- **主张（asserted 措辞）**：笔记记录（一手实测，尚未独立验证）：PR #1423 合并版实现下，对 llama-3 词表头（H=4096, V=128256, bf16），融合线性 KL 相对 PyTorch 朴素组合路径在 BT=4096 时全流程峰值显存 12072 MB → 6594 MB（1.83×），收益随 BT 单调上升（1.13×@1024 → 1.52×@2048 → 1.83×@4096）；同时 full 时间持平（0.90×）——forward 变慢 / backward 变快只是 gradient-in-forward 的计时重排，不是代价。
- **scope**：Liger-Kernel PR #1423 合并版（squash `f6385e9`）；llama-3 词表头 H=4096 / V=128256 / bf16；显存与计时为开发期 RTX 4060 实测（笔记自标"开发期数据"）；A100 评审回复数字归草案 B，两卡口径不混用。
- **falsifiers**：
  - 复现中 full 时间显著偏离 1.0×（如 <0.8× 或 >1.2×）且无法用计时重排解释；
  - 复现中峰值显存收益消失，或收益不随 BT 增大而上升。
- **建议 evidence（locator + 已验证 quote）**：
  - §3.4 内存账本表：

    ```text
    | PyTorch 基线 | logits / log_softmax 输出 / q 的 fp32 副本 / 中间量 / backward 重算的 softmax，各 ~2.05GB | **12072 MB** |
    | 本算子 | X、dX（各 33MB）· W、dW（各 1.05GB）· loss_1d（16KB）· 瞬时块临时 | **6594 MB**（**1.83×**） |
    ```

  - §3.5 时间守恒表：

    ```text
    | **full** | **187.8 ms** | **209.7 ms** | **0.90× 持平** |
    ```

  - §3.4 收益单调性；§8 方法论第 1 条：

    ```text
    **融合损失的收益模型是内存不是速度**：总计算量守恒（full 0.90×），红利是"不物化"；评估先算 $BT{\times}V$ 字节账本。
    ```

    ```text
    1.13×（BT=1024）→ 1.52×（2048）→ 1.83×（4096）随 BT 单调上升
    ```

### 草案 B：`claim-liger-fusedkl-dtype-dependent-gain`

- **title（建议）**：融合线性 KL 对 torch 的基准收益依赖 dtype：bf16/fp16 显著为正，fp32 无收益
- **主张（asserted 措辞）**：PR #1423 评审回复基准（笔记记录，尚未独立验证）报告：A100 bf16 速度 1.43–1.96×、显存 −87~89%；T4 fp16 速度 1.69×、显存 −73.5%；A100 fp32 速度 0.94×–1.16×（无收益，PR 内如实披露）。
- **scope**：PR #1423 评审回复（issuecomment-5654867464）报告的数字；A100 与 Kaggle T4；bf16/fp16/fp32 三种 dtype；显存口径为段级（区别于草案 A 的 4060 全流程口径）。
- **falsifiers**：
  - 复现 fp32 下出现稳定 >1.2× 收益；
  - 或 bf16/fp16 收益复现跌至 ~1.0×、显存节省大幅缩水。
- **建议 evidence**（§4.4 表，三行均已验证）：

    ```text
    | A100 / bf16 | 1.43–1.96× | −87~89% |
    | T4 / fp16 | 1.69× | −73.5% |
    | A100 / fp32 | **0.94×–1.16×**（诚实披露：fp32 无收益） | — |
    ```

## 2 · liger-pr1424-deepseek-v3.md —— 结论：适合立卡，建议 2 张（另 1 张可选）

### 草案 C：`claim-liger-dsv3-flce-seq-scaling-memory`

- **title（建议）**：Liger FLCE 使 DeepSeek-V3 训练显存节省随 seq 增长扩大（16K 时 50%，32K 时 HF OOM）
- **主张（asserted 措辞）**：笔记记录（一手实测，尚未独立验证）：A100 bf16、真实 129280 词表、精简配置（2 层 + 16 experts top-2，已在 PR 披露）、随机初始化、fwd+bwd 无 optimizer step 条件下，HF vs Liger 训练峰值显存：2K 时 13.1 → 12.61 GiB（省 4%），8K 时 26.18 → 16.4 GiB（37%），16K 时 46.06 → 23.15 GiB（50%），32K 时 HF OOM 而 Liger 36.64 GiB；HF 管线边际成本 ≈ +2.4 GiB / 1K tokens；所有 cell 的 loss 相对误差 ≤ 7e-06。
- **scope**：A100 80GB / torch 2.11.0+cu130 / transformers 5.8.1；精简模型配置（非完整 61 层，须随卡披露）；测量口径 fwd+bwd、无 optimizer step、随机初始化（对齐 #1390 仓库先例）。
- **falsifiers**：
  - 重跑显存节省不随 seq 单调增长；
  - 或 16K 处节省显著低于 50%（如 <30%）；
  - 或同配置 loss 相对误差远超 7e-06。
- **建议 evidence**（§5.2 表 + §2.1 + §00 卡片，均已验证）：

    ```text
    | 1 × 2048 | 13.1 GiB | 12.61 GiB | 4% |
    | 1 × 8192 | 26.18 | 16.4 | 37% |
    | 1 × 16384 | 46.06 | 23.15 | **50%** |
    | 1 × 32768 | **OOM** | 36.64 | — |
    ```

    ```text
    A100 实测边际成本 **每多 1K tokens ≈ +2.4 GiB**
    所有 cell 的 loss 相对误差 ≤ 7e-06
    A100 bf16 显存：2K +4% → 16K **+50%**，32K 时 HF OOM 而 Liger 36.6 GiB；吞吐 0.97×–1.00×（真实模型 lm_head 占参 0.14% → 端到端 ≈1.00×）
    ```

### 草案 D：`claim-liger-dsv3-single-shot-memory-false-positive`

- **title（建议）**：单发显存测量系统性低估稳态训练需求（首次迭代尚无保留梯度）
- **主张（asserted 措辞）**：笔记记录（一手排障案例，尚未独立验证）：DSv3 基准战役（Kaggle T4 15GB, fp16, torch 2.10）中，单发测量 11.43 GiB 显示"能放下"，而稳态训练循环需求 ≈15.4 GiB（权重 4.46 + 已保留 grads 4.25 + fp32 dW 累加 3.45 + fp16 cast）必然 OOM——首次迭代还没有保留的 `.grad`，单次 `max_memory_allocated` ≠ 稳态训练显存。
- **scope**：Kaggle T4 15GB / torch 2.10.0+cu128 / 含 optimizer 梯度累积的训练循环、宽词表头（[129280, 7168] 的 fp32 dW 累加场景）；主张的普适表述"单发 ≠ 稳态"以此场景为证据。
- **falsifiers**：
  - 在同类训练循环中，单发 max_memory_allocated 与多轮稳态峰值一致（差异 <5%）；
  - 或按笔记 v1 配置复现，单发测量也 OOM。
- **建议 evidence**（§5.3，均已验证）：

    ```text
    3. **v4（OOM 消息给出答案）**：失败请求正是 fp32 `[V,H]` dW 累加缓冲 = **3.45 GiB**。稳态训练循环的真实需求：
    **v1 单发测量"11.43 GiB 能放下"是假阳性** —— 第 1 次迭代还没有保留的 `.grad`。单次 `max_memory_allocated` ≠ 稳态训练显存，基准必须跑循环。
    ```

- 备注：这是三篇笔记里**复用价值最高**的一张候选——版本无关、复现成本最低（任何 GPU 环境即可做一致性对照）、直接约束以后所有显存基准的做法。

### 可选草案 E：`claim-liger-dsv3-endtoend-throughput-parity`（优先级低）

- **主张（实测部分）**：A100 bf16、b=1 seq 4096 变深度扫描，Liger/HF 吞吐 0.97× / 0.98× / 1.00×（2/4/8 层）；T4 上 loss 段吞吐 0.27×–0.36×。
- **主张（推断部分，须与实测分开表述）**："真实 61 层模型 lm_head 占参 ~0.14% → 端到端 ≈ 1.00×" 是参数占比推断，不是实测。
- **falsifiers**：同口径复现中端到端吞吐比 <0.9×；或 loss 段减速无法被 lm_head 参数占比稀释解释。
- **建议 evidence**（§5.2 吞吐表 + §5.3 v5，均已验证）：

    ```text
    | 2 | 27% | 8457 | 8172 | 0.97× |
    | 4 | 18% | 5117 | 5039 | 0.98× |
    | 8 | 10% | 2871 | 2862 | 1.00× |
    跑通，得到 **Liger 0.27× / 0.36× HF tok/s**（L2/L4）。
    ```

- 若主人只想立两张，这张可放弃（其结论已被草案 C 的"显存是主收益"覆盖大半）。

## 3 · liger-pr1501-deepseek-v2.md —— 结论：不适合立卡，建议留在 L1

### 理由

1. **本篇正是原始疑虑描述的那类内容**。主线是 transformers 5.0.0 与 5.16.1 的命名漂移考古：

    ```text
    | 5.0.0（Kaggle 实装） | **只有 `n_routed_experts`** | `num_local_experts`（+`n_routed_experts` 别名） |
    E   AttributeError: 'DeepseekV2Config' object has no attribute 'num_local_experts'
    ```

   该 bug 已随 PR #1501 合入永久修复——"5.0.0 的 DeepseekV2Config 只有 n_routed_experts"这类快照事实对未来的任何选型 / 实验决策都不再构成输入。它已经以"合入的 PR + 修复的 bug"形式固化，不需要 claim 机制追踪。

2. **T4 bf16 发现是漂移中的环境事实**，验证成本极低：

    ```text
    torch 2.10 下 `supports_bfloat16()` 为 True，bf16 收敛测试在 T4 上真实执行并通过
    ```

   今天立卡很快 stale；真需要时一行 API 现场重验即可，不值得走卡的"待验证"流程。

3. **真正有长期价值的是两条方法论**——「instance 测试（rebind）与收敛测试（类替换构造）覆盖不同失败面」「本地最新版全绿 ≠ 兼容，落后环境是最便宜的试金石」：

    ```text
    **两个测试覆盖的失败面不同：rebind 路径 vs 构造路径。**
    本地最新版全绿 ≠ 用户真实环境 OK；一个"落后"的环境是最便宜的兼容性试金石
    ```

   但它们是经验原则 / 叙事，无法写成单一可证伪主张；硬写成本案的历史事实主张（"v1 实例测试过而收敛测试挂"），就退回第 1 条的版本快照问题。其价值已在 L1 §3.4 教训与 §8 方法论清单完整表达，无需重复承载。

4. **对照组价值**：本篇恰好是 TODO 疑虑的正面例证——同批三篇里，#1423 / #1424 的基准与机制主张值得立卡，#1501 的内容应整体留在 L1。原始疑虑应按**篇内内容类型**区分对待，而不是按"篇"一刀切。

## 4 · 对原始疑虑的直接回答

「版本依赖强、复现成本高的内容可能更适合留在 L1」——**部分成立，需要拆开看**：

1. **复现成本高不构成否决**：三篇都是一手数据 + PR 原始日志，证据地位好于论文自报；立卡后 status 仍是 asserted，"独立验证"是卡上待验证栏的工作，不是立卡前提。
2. **版本依赖强是 scope 问题，不是否决**：把 commit / 软件版本钉进 scope（草案 A–E 均如此处理），基准类主张就变成可判定的快照主张；上游继续演进属于 review_due 重验范畴。
3. **真正该留 L1 的是三类**：版本考古快照（决策输入价值已归零）、教科书数学推导、过程复盘叙事。按这个标准：#1501 整篇属于这三类 → 留 L1；#1423 / #1424 的基准与机制主张剥离出来立卡（草案 A–E），其余部分留 L1。
